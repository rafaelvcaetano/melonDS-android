## How to read the evidence

- The scans provide **static evidence**. A post-fix test is described as dynamic
  only where the report or register records an execution. Source analysis does
  not establish a dynamically failing test before the correction.
- In second-campaign cards, “focused regression” and final host/JVM/NDK/ART
  checks refer to a suite or class of post-fix tests. They do not establish an
  individual dynamic reproduction of each trigger. An individual RED/GREEN
  result is claimed only where this document names the case, command or outcome.
- `Open` in the Security results interface is a service workflow state. The
  technical disposition—corrected, not applicable, informational or dependent
  on an unverified external control—is recorded separately in the CSV.
- Source links pin the affected location to its reviewed revision. First-campaign
  integration links retain that campaign's historical pair; second-campaign
  links pin `0018cddb`/`ac5e6ba0`, including the Action Replay and G.711 refinements
  and the later x86-64 JIT correction. They do not change the original snapshots.
- Counterevidence records normal conditions or controls that limit a claim.
  It does not automatically disprove a confirmed path. Limitations prevent the
  report from extending impact beyond what the evidence demonstrates.

### Additional cause outside the scan count

CI after the first push produced an actual RED result for Linux x86-64 JIT
Thumb/DTCM handling: that backend could still fold a literal without an
invalidation owner. This was a pre-existing functional gap exposed after the
scan, not a Security occurrence or a 102nd card. The x86-64 result is separate
from Android ARM64 execution. Final core `ac5e6ba0` contains the correction;
the Linux x86-64 JIT check then passed in core run `41704485288` and app run
`41704565464`. The G.711 and Action Replay cases below refine occurrences
already counted. Their context and limits are in the
